1. Overview

HRIS + Payroll exposes a versioned REST API for multi-company Philippine HR operations: organization structure, employee lifecycle, attendance/DTR, leave, shifts, payroll runs, government compliance, ESS, recruitment, documents, assets, workflows, analytics, SaaS subscription, and platform administration.

Surface Prefix Auth
Infrastructure /health, /ready Public
Authentication /api/v1/auth/* Public (rate-limited)
Public SaaS /api/v1/public/*, /api/v1/enterprise/* Public
Tenant account /api/v1/account/* Bearer token + company context
Platform admin /api/v1/platform/* Bearer token + super-admin / platform permissions

Content type for JSON bodies: application/json unless uploading multipart files (employee import, documents, COA attachments).

2. Authentication & Tokens

2.1 Token types

Token Lifetime (typical) Use
Access token ~60 minutes (ACCESS_TOKEN_TTL_MINUTES) Authorization: Bearer <accessToken>
Refresh token ~30 days (REFRESH_TOKEN_TTL_DAYS) POST /api/v1/auth/refresh
MFA challenge Until completed / expired Login returns requiresMfa + userId

Default mode (AUTH_MODE=local) uses Adonis opaque access tokens. Enterprise platform SSO JWTs apply when AUTH_MODE=platform|dual (JWKS verification via PLATFORM_* env).

Successful login / invite accept / MFA verify / refresh returns a structure similar to:

{
  "success": true,
  "data": {
    "user": {
      "id": "uuid",
      "email": "employee@identity.local",
      "fullName": "Demo Employee",
      "permissions": ["employee.view", "payroll.view"],
      "memberships": [{ "companyId": "uuid", "companyCode": "DEMO", "role": "company_admin" }]
    },
    "accessToken": "…",
    "refreshToken": "…",
    "expiresIn": 3600
  }
}

When MFA is required at login:

{
  "success": true,
  "data": {
    "requiresMfa": true,
    "userId": "…"
  }
}

Then call POST /api/v1/auth/mfa/verify with { "userId", "code" } (TOTP or recovery code).

3. Multi-Company Tenancy

  • Company membership is bound to the authenticated user via UserCompanyMembership.
  • Account routes require auth → companyContext → companyMembership → saasSubscription → rateLimit → audit → securityEvent.
  • Send X-Company-Id when the user belongs to more than one company.
  • SaaS middleware may return 402 (TRIAL_EXPIRED, SUBSCRIPTION_REQUIRED) when the tenant subscription/trial blocks writes.
  • IP allowlists (hardening) may return 403 IP_NOT_ALLOWED.

Always send the access token on account and platform routes. Do not rely on company id alone.

Exempt from membership/subscription checks (typical): /auth/*, /account/me, /account/saas/*, /health, /ready.

4. Headers & Conventions

Header Required Description
Authorization Account / Platform Bearer <accessToken>
Content-Type JSON writes application/json
X-Company-Id Multi-company users Active company UUID
X-Device-Source Optional e.g. mobile (Expo)
X-Device-Fingerprint Optional Auth audit metadata
Accept Optional Prefer application/json

Path params: UUIDs unless noted (employee numbers, public branding codes).

Pagination: list endpoints typically accept page, perPage (and often search / filters). Check OpenAPI or controller validators for each operation.

Idempotency: Prefer safe retries on GET. Mutations (POST/PATCH/DELETE) should not be blindly retried without client-side guards (especially payroll compute / approve / lock).

5. Error Model

Success envelope:

{
  "success": true,
  "message": "…",
  "data": {},
  "meta": { "page": 1, "perPage": 25, "total": 0, "totalPages": 0 }
}

Error envelope:

{
  "success": false,
  "message": "…",
  "errors": [{ "field": "email", "message": "…" }],
  "code": "VALIDATION_ERROR"
}
Status Meaning
200 / 201 Success / created
204 Delete success (when used)
400 Validation / business rule (LOGIN_FAILED, MFA_FAILED, …)
401 Missing or invalid token (UNAUTHENTICATED, INVALID_REFRESH_TOKEN)
402 Trial/subscription required
403 Forbidden (RBAC, company access, IP allowlist)
404 Resource not found
409 Conflict
422 Invalid state transition (e.g. payroll run status)
429 Rate limited
500 Server error

6. Rate Limiting & Throttling

  • Auth routes use dedicated authRateLimit middleware (tight per-IP limits).
  • Account routes use per-user rateLimit middleware.
  • Attendance clock / offline sync endpoints are tuned for higher frequency.
  • Respect 429 responses; back off and retry with jitter.

Exact numeric quotas are environment-configurable — treat OpenAPI/Swagger as the contract for request shapes; treat ops config for quotas.

10. Common Workflows

10.1 Login → dashboard

  1. POST /api/v1/auth/login
  2. If requiresMfa, complete POST /api/v1/auth/mfa/verify
  3. Store tokens; send Authorization: Bearer …
  4. If multi-company, set X-Company-Id
  5. GET /api/v1/account/me and GET /api/v1/account/dashboard

10.2 ESS clock in

  1. Authenticate as employee with ess.access
  2. GET /api/v1/account/ess/attendance/status
  3. POST /api/v1/account/ess/attendance/clock with punch payload (and geofence fields when required)

10.3 Payroll compute → approve → lock

  1. Ensure pay period exists (POST /api/v1/account/payroll/periods)
  2. POST /api/v1/account/payroll/runs
  3. POST /api/v1/account/payroll/runs/:id/compute
  4. Review GET …/runs/:id/register
  5. POST …/submit → POST …/approve → POST …/lock
  6. Optional: GET …/bank-file, payslip downloads

10.4 Leave request → approve

  1. ESS: POST /api/v1/account/ess/leave/requests
  2. Approver: workflow inbox or PATCH /api/v1/account/leave/requests/:id/approve

10.5 Token refresh

  1. On 401, call POST /api/v1/auth/refresh with refreshToken
  2. Retry original request with new access token
  3. If refresh fails, force re-login

10.6 Accept invite

  1. Admin creates user → invite email
  2. User opens /invite with token
  3. POST /api/v1/auth/accept-invite with token + password
  4. Continue as authenticated session
