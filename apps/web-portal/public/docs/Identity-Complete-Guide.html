Part 1 — User Manual

Chapter 1 — Introduction

Purpose

Identity Service is the central login hub for WMSU Campus Information Systems. Users sign in once at the WMSU Portal, then launch only the platforms assigned to them:

  • USiS — Enrollment / student information
  • TORMS — Transcripts and official records
  • ULMIS — Library staff, OPAC, kiosk
  • UFMS — Budget, accounting, procurement, POS
  • DocsTrack (UDMS) — Document tracking and approvals
  • UIMS — Inventory and assets

Benefits

  • One password for multiple systems
  • Platform grants control which tiles appear on the launcher
  • Identity roles map to permission packs inside each app (student vs registrar vs employee)
  • RS256 SSO tokens platforms verify via JWKS

Chapter 3 — Signing In

  1. Open the Identity portal.
  2. Enter your email and password (use the eye icon to show or hide the password).
  3. Click Login.
  4. On success you land on the home / launcher screen.

Demo accounts (non-production)

Set DEMO_SEED_PASSWORD in the API env, then run node ace db:seed. Accounts:

Email Typical use
admin@identity.local Full admin + all platforms
student@identity.local Student role — USiS student portal, library/OPAC/kiosk, records self-service when assigned
employee@identity.local Employee — multiple platforms; menus depend on roles (not full registrar by default)
nodocs@identity.local Library platforms only (no DocsTrack)

If login fails, check caps lock, email spelling, and that your account status is active.

Chapter 4 — Platform Launcher

After login, the portal lists platforms you are allowed to open.

  1. Choose a platform card (USiS, TORMS, Library, UFMS Finance, DocsTrack, UIMS, …).
  2. The portal opens the platform SSO callback with your tokens.
  3. Continue working inside that platform.

Platforms you are not granted do not appear (or cannot be launched).

Chapter 5 — Roles, platforms, and in-app access

Platforms control launcher tiles and SSO into an app (enrollment, records, library, finance, docstrack, inventory, …).

Roles control what you can do inside each app after launch. Examples:

  • student — USiS student portal only; ULMIS member/OPAC; not registrar staff modules
  • registrar — USiS registrar workflows; ULMIS staff when library is granted
  • employee — launch-only unless another role is assigned
  • identity_admin — full access on assigned platforms

Coarse permissions such as enrollment.access mean “may use USiS,” not “see every registrar menu.” Portal Admin shows a short access note under each role when editing users.

Chapter 6 — Administrator Console

Identity Admins can:

  • List and create users
  • Assign roles and platform grants
  • Manage role permissions
  • Review available platforms

Use Portal Admin in the WMSU Portal (Identity administrators) or the Admin API in the API Specs Manual.

Assign both roles and platforms. Role checkboxes include access notes that match in-app permission packs.

Chapter 7 — Enrollment Partner Overview

A third-party enrollment system can create/update student accounts via API key.

  • Upsert one or many students
  • Deactivate withdrawn/graduated students
  • Always Library-only platforms

Details: enrollment-integration.md.

Chapter 8 — Dual-Mode SSO (platforms)

Each platform (USiS, ULMIS, UFMS, DocsTrack, …) can keep local login while Identity SSO is rolled out.

On the platform feature branch / config:

  1. Set AUTH_MODE=dual (or platform when fully cut over)
  2. Point Identity URL / JWKS / issuer / audience at this service
  3. Optionally map tenant/company IDs for JWT app claims
  4. Accept SSO callback tokens from the Identity launcher

Leave AUTH_MODE=local until Identity is ready — existing platform logins stay unchanged.

Chapter 10 — Frequently Asked Questions

Why don’t I see UFMS Finance or USiS?
Your account is not granted that platform code yet — ask an identity admin to assign finance or enrollment.

Why do I only see the student menu in USiS?
Your Identity role is student (or your permission pack is student-only). Registrar menus require the registrar role.

I forgot my password.
Contact an Identity administrator to reset it (self-serve reset may be added later).

Can I use the same Identity account on ULMIS before SSO is enabled?
Platforms on AUTH_MODE=local use their own accounts until dual/platform mode is configured.

Where are signing keys?
On the API host under apps/api/keys/ (private key is never committed to git).

Chapter 11 — Troubleshooting

Symptom Check
Login 401 Password, account disabled, API running
Launcher opens but platform rejects token JWKS URL, issuer/audience, clock skew
Student sees registrar menus Remove registrar/staff roles; keep student only in Portal Admin
Enrollment 401 X-Service-Api-Key vs ENROLLMENT_SERVICE_API_KEY
/auth/me unauthorized Missing Bearer token or wrong public key

Chapter 12 — Glossary

Enrollment externalId Stable id from the enrollment system

Chapter 13 — Best Practices

  • Rotate enrollment API keys periodically.
  • Never commit .env or *.pem private keys.
  • Prefer dual mode during migration; monitor SSO failures before disabling local login.
  • Assign platforms and roles together; read the access notes in Portal Admin.
  • Do not grant registrar roles to student accounts.
  • Use unique emails per person; link via externalId for enrollment.

Chapter 14 — Task: Create a staff user

  1. Sign in as Identity Admin.
  2. Open Admin → Users → Create.
  3. Enter email, name, password.
  4. Assign role (e.g. employee or registrar) and platforms (enrollment, library, finance, … as needed).
  5. Save and verify the user can log in.

Chapter 15 — Task: Disable a withdrawn student

Via enrollment API:
POST /api/v1/integrations/enrollment/students/{externalId}/deactivate with service API key.

Via admin:
Set user status to disabled.

Confirm the student can no longer log in to Identity.

Chapter 16 — Task: Configure platform dual SSO

  1. Deploy Identity API with JWKS reachable from the platform.
  2. On the platform, set AUTH_MODE=dual and Identity/JWKS/issuer/audience env vars.
  3. From Identity portal, launch the platform and confirm callback login.
  4. Confirm local login still works until you cut over.
