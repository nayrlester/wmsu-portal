1. Overview

ULMIS exposes a versioned REST API for university library operations: catalog/inventory, members, circulation, reservations, fines, OPAC, member portal, digital repository, self-service kiosk, queue/locator hardware platform, attendance, reports, and campus integrations.

Surface Prefix Auth
Infrastructure /health, /api/v1/docs* Public
Authentication /api/v1/auth/* Public (login/register/refresh)
Tenant resolve /api/v1/tenants/resolve Public
Public OPAC / queue /api/v1/public/* Tenant slug header
Staff LMS /api/v1/* (books, members, …) Bearer JWT + tenant
Member portal /api/v1/portal/* Bearer JWT (member) + tenant
Kiosk self-service /api/v1/kiosk/* Device code + API key + tenant
Hardware admin /api/v1/hardware/* Bearer JWT + tenant
Integrations /api/v1/integrations/* Bearer JWT + tenant

Content type for JSON bodies: application/json unless uploading multipart files (catalog CSV/XLSX, digital files).

Approximate route count: 133 HTTP registrations (plus GET /health).

Clients (local):

App Port Auth
Staff web (apps/web) 5173 JWT + X-Tenant-Slug
Public OPAC (apps/opac) 5174 X-Tenant-Slug
Kiosk (apps/kiosk) 5175 Kiosk headers + tenant
API (apps/api) 3333 —

See also CLIENT_APPS.md.

2. Authentication & Tokens

2.1 Token types

Token Lifetime (typical) Use
Access token (JWT) Short-lived (expiresIn) Authorization: Bearer <accessToken>
Refresh token Longer-lived POST /api/v1/auth/refresh
Kiosk API key Until rotated X-Kiosk-Api-Key (plaintext shown once)

Default university mode uses local jose JWTs. Enterprise platform SSO JWTs apply when AUTH_MODE=platform|dual.

Successful login returns a structure similar to:

{
  "success": true,
  "data": {
    "user": {
      "id": "uuid",
      "email": "admin@university.library",
      "fullName": "Library Admin",
      "tenantId": "uuid"
    },
    "tokens": {
      "accessToken": "…",
      "refreshToken": "…",
      "expiresIn": 900,
      "tokenType": "Bearer"
    }
  }
}

Exact field nesting follows OpenAPI / runtime responses — always prefer the live Swagger schema.

2.2 Auth endpoints

Method Path Purpose

POST /api/v1/auth/login Email/password login
POST /api/v1/auth/refresh Rotate access token
GET /api/v1/auth/me Current authenticated user
POST /api/v1/auth/logout Invalidate session / refresh

2.3 Demo / training credentials (University Identity)

Prefer University Identity demo accounts (seeded when DEMO_SEED_PASSWORD is set):

Email Typical use
admin@identity.local All platforms + Identity admin
employee@identity.local Library + HRIS + DocsTrack
student@identity.local Library / OPAC only
nodocs@identity.local Library + HRIS (no DocsTrack)

Password: DEMO_SEED_PASSWORD from the Identity API environment. Legacy local bootstrap email admin@university.library (tenant slug ulmis) may still exist for direct Library login — rotate immediately and do not reuse shared demo passwords in production.

3. Multi-Tenancy

  • Every institution is a tenant identified by slug (e.g. ulmis).
  • Resolve tenant metadata: GET /api/v1/tenants/resolve?slug=ulmis (or equivalent query per OpenAPI).
  • Staff clients send X-Tenant-Slug: ulmis on API calls.
  • Public OPAC and kiosk also require the tenant slug header.
  • Data isolation is enforced in repositories and policies (catalog, members, loans, fines, etc.).

Always send the access token and tenant context on protected staff/portal routes. Do not rely on slug alone.

Update tenant branding / preferences: GET|PATCH /api/v1/tenant (authenticated staff with settings permissions).

4. Headers & Conventions

Header Required Description
Authorization Staff / Portal Bearer <accessToken>
X-Tenant-Slug Most routes Institution slug (e.g. ulmis)
X-Kiosk-Device-Code Kiosk routes Registered device code (exact match)
X-Kiosk-Api-Key Kiosk routes Full plaintext key (ksk_…)
Content-Type JSON writes application/json
Accept Optional Prefer application/json

Path params: UUIDs unless noted.

Pagination: list endpoints typically accept page, perPage (and often q for search). Defaults: page=1, perPage=25 (max 100).

Idempotency: Prefer safe retries on GET. Mutations (POST/PUT/PATCH/DELETE) should not be blindly retried without client-side guards.

Currency: Monetary amounts are in PHP (₱) for university deployment.

5. Error Model

Failed requests generally return JSON with an error payload, for example:

{
  "success": false,
  "error": {
    "message": "Unauthorized",
    "code": "E_UNAUTHORIZED"
  }
}

Validation failures may include field-level messages from VineJS. HTTP status codes follow REST norms:

Status Meaning
200 / 201 Success
400 Validation / bad request
401 Missing or invalid token / kiosk key
403 Authenticated but forbidden (permission / policy)
404 Resource not found
409 Conflict (duplicate barcode, state machine)
413 Payload too large
429 Rate limited (when configured)
501 Integration not configured / not verified (LDAP, SSO)
500 Server error

Borrow blocks (overdue, unpaid fines, membership) return structured policy errors from circulation services — treat as business-rule failures, not transport errors.

6. Client Surfaces

6.1 Staff web

Full JWT-protected LMS: books, members, borrowings, reservations, fines, reports, users, settings, digital, attendance, integrations, Kiosk Platform, staff OPAC.

6.2 Public OPAC

Unauthenticated catalog search and detail (citations). Optional public queue board for display screens.

6.3 Member portal

Authenticated member: profile/loans, renew, reservations, reading lists, fine visibility (via portal + fines APIs as exposed).

6.4 Kiosk

Device-authenticated self-service: session, heartbeat, patron lookup, account, history, checkout, return.

6.5 Hardware / Kiosk Platform (staff)

Register/rotate kiosk devices, queue tickets, call-next, locations, resource locate. RFID routes exist but the RFID module claim is excluded from software-complete readiness.

fines:read / collect / waive / adjust Fines
reservations:read / create / cancel / fulfill Holds
digital:read / create / access / delete Repository / e-resources
search:query Staff search
ai:query AI assistant
analytics:read Dashboard analytics
reports:export Operational reports
audit:read / audit:export Audit logs
activity:read Activity feed

Seeded roles: admin (all), librarian, staff, member — see rbac_service.ts.

Current user: GET /api/v1/auth/me (includes roles/permissions as implemented).

9. Core Resource Schemas

Canonical schemas live in OpenAPI (components/schemas). Conceptual shapes:

Book (title)

id, title, authors, isbn, category, description, copy counts / availability fields, timestamps.

Copy

id, bookId, barcode, status (available | on_loan | lost | …), location metadata.

Member

id, memberNumber, fullName, email, membershipType, status (pending | active | suspended | …).

Borrowing

id, memberId, copyId, status, borrowedAt, dueAt, returnedAt, renew count.

Fine

id, memberId, amount, currency (PHP), status, line items / payments.

Kiosk device

id, deviceCode, label, location, status, lastHeartbeatAt — API key never returned after create/rotate response.

10. Common Workflows

10.1 Staff login → catalog

  1. POST /api/v1/auth/login with email, password, tenant context as required.
  2. Store access + refresh tokens.
  3. Call GET /api/v1/books with Authorization + X-Tenant-Slug.

10.2 Checkout / return (staff)

  1. Resolve member and available copy.
  2. POST /api/v1/borrowings/checkout (or request → approve → checkout).
  3. On return: POST /api/v1/borrowings/{id}/return (fines may be created for overdue).

10.3 Public OPAC search

  1. Send X-Tenant-Slug: ulmis.
  2. GET /api/v1/public/opac/search?q=….
  3. GET /api/v1/public/opac/books/{id} and /citations.

10.4 Kiosk self-checkout

  1. Staff registers device; copies full ksk_… key once.
  2. Kiosk app stores device code + key + tenant ulmis.
  3. GET /api/v1/kiosk/session then patron lookup → POST /api/v1/kiosk/checkout.

10.5 Catalog import

  1. Multipart POST /api/v1/catalog/import/csv or /xlsx, or JSON body for /marc.
  2. Review GET /api/v1/catalog/books/{id}/versions for history.

10.6 Scheduled report email

  1. Configure schedule on PATCH /api/v1/tenant (report prefs).
  2. Ensure SMTP_* env and node ace queue:listen (or equivalent) are running.
  3. Reports also available on-demand via GET /api/v1/reports/{type}.

11. Kiosk Device Auth

Headers required on every /api/v1/kiosk/* call:

X-Tenant-Slug: ulmis
X-Kiosk-Device-Code: KIOSK-001
X-Kiosk-Api-Key: ksk_••••••••
Pitfall Fix
Using location name as tenant Use slug ulmis, not a city/campus label
Wrong device code Exact match to registered code (e.g. KIOSK-001 ≠ KIOSK-01)
Truncated API key Re-rotate key; copy the full value once

Rotate: POST /api/v1/hardware/kiosks/{id}/rotate-key — previous key is invalidated.
